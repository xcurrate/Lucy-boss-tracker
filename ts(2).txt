# MASTER PROMPT — DRAGNEEL CUSTOM REMINDER SYSTEM

## 0. ROLE, OBJECTIVE, AND IMPLEMENTATION RULES

You are a senior Node.js Discord bot engineer. Extend the existing Dragneel Discord bot with a complete Custom Reminder system and server-level reminder message settings.

The goal is to reproduce the useful Custom Reminder and inventory capabilities shown in the supplied Reaction Bot references, while preserving Dragneel's existing architecture and behavior.

This prompt is the complete implementation specification. Follow every applicable requirement. If the repository's actual implementation differs from an assumption in this prompt, inspect the code first, preserve working behavior, and report the discrepancy rather than inventing APIs or silently removing functionality.

Mandatory workflow:
1. Inspect the repository, entry points, command framework, event handlers, storage/database, permission helpers, prefix resolver, reminder engine, embed utilities, media utilities, and tests before editing.
2. Identify the exact existing integration points and produce a concise implementation plan.
3. Implement incrementally using existing conventions. Avoid unrelated refactoring or rewriting whole modules.
4. Preserve existing bot features and backward compatibility.
5. Add or update tests, run the relevant test suite, and report actual results. Never claim a test or feature succeeded unless it was actually run and verified.
6. If a requirement cannot be implemented safely because a necessary existing hook or API is absent, explain the limitation and do not fabricate behavior.

## 1. EXISTING DRAGNEEL PROJECT CONTEXT

- Dragneel already has an existing Developer ID authorization system. Reuse it; do not create a second developer ID system or duplicate developer configuration.
- Dragneel already provides reminder functionality for the relevant existing actions, including Pray, Curse, Hunt, and Battle. Preserve the actual existing Lucy-related behavior after inspecting the repository.

## 2. CORE ARCHITECTURE: EXISTING ENGINE, CONFIGURATION LAYERS

Dragneel already has reminder delivery for the relevant actions. Extend the message/configuration resolution layer of that existing engine; do not rebuild the engine.

Keep these configuration scopes separate:

A. Built-in Dragneel default messages — the original fallback behavior shipped with the bot.
B. Per-guild Server Default Reminder settings — configured by that server's administrators and applied to members without an applicable active Custom Reminder.
C. Per-user Owned Custom Reminders — personal reminders obtained by redeeming a developer-issued claim.
D. Global Developer Templates — source templates used to issue Custom Reminders.
E. Pending Developer Awards / Claims — one-time grants assigned to specific recipients before redemption.

Never store personal Custom Reminder edits in server settings. Never store server settings in global templates. Never mutate a global template when a user edits an owned copy. Redeeming a claim must create an independent owned instance initialized from its template.

## 3. REMINDER CATEGORIES AND FORMATS

The Custom Reminder system must support exactly these three predefined categories in this version:

1. `PRAY_CURSE` — Pray / Curse Reminder.
2. `HUNT_BATTLE` — Hunt / Battle Reminder.
3. `LUCY` — Lucy Reminder.

Each category supports two distinct message formats:

- `NORMAL`: ordinary Discord message content.
- `EMBED`: a configurable Discord rich embed.

The six supported category-format combinations are:
- Pray/Curse Normal.
- Pray/Curse Embed.
- Hunt/Battle Normal.
- Hunt/Battle Embed.
- Lucy Normal.
- Lucy Embed.

Important distinctions:
- Category describes WHAT the reminder is associated with.
- Format describes HOW the reminder is displayed.
- Store category and format as separate properties.
- Do not model Normal and Embed as separate categories.
- Do not hardcode category-specific message content in the runtime engine.
- Developers must be able to create templates for all six combinations.
- A user may own multiple reminders, including multiple reminders of the same category and different formats. Each owned reminder has its own ID and status.
- Preserve category and format when a reminder is awarded, redeemed, edited, shared, or transferred.
- Do not add a fourth `DAILY` category merely because Daily Reminder appeared as an illustrative inventory label in an earlier example. The supported categories for this version are the three listed above. Keep the data model reasonably extensible without exposing unsupported categories.

### 3.1 Lucy semantics — important

`LUCY` means **Say Lucy**: the reminder sends/says the configured Lucy content.

It does NOT mean a generic reminder for Lucy activity, Lucy hunt, Lucy battle, or an assumed Lucy event. Do not invent Lucy event hooks. Inspect the existing Dragneel Lucy-related command/action and reminder behavior, then connect the Say Lucy reminder to the real existing behavior where applicable. If the repository does not expose a suitable trigger, report that and do not fabricate one.

## 4. SERVER DEFAULT REMINDER SETTINGS — EXISTING `s` SETTINGS NAMESPACE

Server default reminder messages are configured through Dragneel's existing server Settings namespace, whose subcommand is `s`.

**Do not create a separate `d r server` namespace or redundant server-reminder command group.** The `r` namespace is for personal Custom Reminder commands; the existing `s` namespace is for server settings.

Use this command convention, with the actual guild prefix resolved dynamically:

- `<PREFIX> s pray set text <MESSAGE>`
- `<PREFIX> s pray reset`
- `<PREFIX> s curse set text <MESSAGE>`
- `<PREFIX> s curse reset`
- `<PREFIX> s hunt set text <MESSAGE>`
- `<PREFIX> s hunt reset`
- `<PREFIX> s battle set text <MESSAGE>`
- `<PREFIX> s battle reset`
- `<PREFIX> s lucy set text <MESSAGE>`
- `<PREFIX> s lucy reset`

These examples express the intended command structure. Inspect the existing Settings command registration and preserve the real category names, aliases, argument parsing, help conventions, and existing embed-setting syntax. Do not break existing commands.

The combined Custom Reminder categories do not require combined server-setting keys. Preserve independent server settings for individual actions when the existing bot exposes them. For example, `s hunt` and `s battle` may have separate server-default message settings even though both belong to the `HUNT_BATTLE` Custom Reminder category. Likewise, Pray and Curse may retain separate settings. Map each existing action to the appropriate Custom Reminder category without merging settings that are currently independent.

For EMBED server settings, reuse an existing settings-command pattern if one exists. Do not invent an incompatible command syntax. If server defaults currently support only text, preserve that behavior and report whether server-default embeds are supported; Custom Reminder embeds remain required.

### 4.1 Server-settings permissions

- Only the Discord server owner or authorized server administrators may modify that guild's server-default reminder settings.
- Check permissions in the target guild and use Dragneel's existing server permission conventions.
- If the repository has no suitable convention, require Discord Administrator permission by default; the guild owner must also be allowed.
- Do not grant server-settings access merely because someone is a Dragneel developer or has a Developer ID.
- Reject unauthorized attempts with a clear message such as: `Only server admins & owners can change this setting.`
- Ordinary users may view help or public settings information if permitted by existing bot conventions, but cannot modify settings.
- Settings are isolated per guild and persist after restarts.
- Reset restores the original built-in Dragneel default for the selected action/category. It must not delete or modify any user's owned Custom Reminder.
- A change in one guild must never affect another guild.

## 5. CUSTOM REMINDER RESOLUTION AND FALLBACK

When the existing Dragneel reminder engine is about to deliver a reminder, resolve the message configuration for the target guild, user, and actual action.

Required precedence:
1. If the user owns an applicable, valid, active Custom Reminder for the relevant category/action, use that user's personalized configuration.
2. If the applicable Custom Reminder is disabled, unavailable, or otherwise not eligible, fall back to that guild's Server Default Reminder configuration.
3. If the guild has no custom server setting for that action, preserve the original built-in Dragneel default behavior.

The fallback behavior is FINAL: **when a user disables a Custom Reminder, that user automatically returns to the Server Default Reminder** for the corresponding category/action. No additional command or new redemption is required.

Additional rules:
- The override is personal. It must not change messages delivered to other members.
- An admin changing server defaults must not overwrite a member's Custom Reminder.
- Editing a Custom Reminder must never modify server defaults.
- The fallback is category/action-specific. Disabling Hunt/Battle must not disable Pray/Curse or Lucy reminders.
- Do not let a reminder for one category override an unrelated category.
- Resolve ownership using Discord user IDs and the relevant guild context where applicable.
- Preserve existing reminder triggers, timing, cooldowns, grinding behavior, and delivery semantics.
- Prevent duplicate reminder delivery and respect Discord rate limits.
- If users can own multiple reminders in the same category, preserve all of them in inventory. Inspect existing intended runtime semantics and implement deterministic selection/delivery without accidental duplicate spam. Do not silently discard or merge owned reminders. Document the resulting behavior.

## 6. DEVELOPER TEMPLATES AND MANUAL GIVEAWAY DISTRIBUTION

Distribution is controlled by the existing Dragneel Developer ID authorization system.

The giveaway winner is selected manually outside this feature. A developer then issues the reminder to the winner. Do not build automatic giveaway detection or integration.

Developer-only operations should support:
- `<PREFIX> r create` — create a reminder template.
- `<PREFIX> r templates` — list available templates.
- `<PREFIX> r give @USER <TEMPLATE_ID>` — award a template to a specific user.
- `<PREFIX> r awards` — inspect issued awards and their statuses.
- `<PREFIX> r revoke <CLAIM_ID>` — revoke an unredeemed pending claim.

Inspect existing command conventions and adapt syntax only when necessary to avoid conflicts. Authorization must use the existing Developer ID system.

### 6.1 Award workflow

1. The developer determines the giveaway winner outside this module.
2. The developer selects a template and issues it to the winner.
3. Verify developer authorization using the existing Developer ID implementation.
4. Validate recipient and template.
5. Create a unique pending claim assigned to that exact Discord user ID.
6. Record issuing developer, template, source/reason (for example, giveaway), creation time, and optional expiry.
7. Send the claim ID and redemption instructions to the recipient via DM.
8. If DM delivery fails, inform the developer and display the claim ID so it can be delivered manually.
9. The assigned winner redeems with `<PREFIX> r redeem <CLAIM_ID>`.
10. Verify recipient ownership, claim validity, expiry, and status.
11. Create a new owned reminder with its own unique reminder ID, initialized from the template.
12. Mark the claim redeemed atomically.
13. Prevent duplicate redemption, unauthorized redemption, and duplicate processing.

Keep these identifiers strictly distinct:
- Template ID: identifies a global developer template.
- Claim ID: identifies a pending award assigned to a recipient.
- Owned Reminder ID: identifies the reminder in a user's inventory.

The inventory must list owned reminder IDs, never template IDs or pending claim IDs.

## 7. USER COMMANDS FOR OWNED CUSTOM REMINDERS

All commands use the existing dynamic per-guild prefix resolver and the existing `r` command namespace where compatible.

### 7.1 Inventory and inspection

- `<PREFIX> r inventory` — list all reminders owned by the invoking user.
- `<PREFIX> r view <REMINDER_ID>` — preview the reminder message/embed.
- `<PREFIX> r info <REMINDER_ID>` — show reminder details.
- `<PREFIX> r active` — list active owned reminders.
- `<PREFIX> r redeem <CLAIM_ID>` — redeem an assigned claim.

Inventory must display, at minimum:
- Owned Reminder ID.
- Display name.
- Category.
- Format (Normal or Embed).
- Active status.
- Shareable status.

Use Discord embeds consistent with Dragneel's existing design conventions. Show a useful empty-inventory response when the user owns no reminders. Never expose another user's private inventory unless an explicitly authorized developer/admin operation requests it.

### 7.2 Customization

- `<PREFIX> r update <REMINDER_ID> <MESSAGE>` — update a Normal message.
- `<PREFIX> r embed <REMINDER_ID> <JSON>` — configure an Embed reminder using validated JSON.
- `<PREFIX> r setcollectible <REMINDER_ID> <COLLECTIBLE>` — set the collectible type, if compatible with the existing collectible system.
- `<PREFIX> r reset <REMINDER_ID>` — restore that owned reminder's template defaults, with confirmation.

Customization must not change the reminder ID, category, format, owner, source template, server defaults, or another reminder.

### 7.3 Activation

- `<PREFIX> r enable <REMINDER_ID>` — activate one owned reminder.
- `<PREFIX> r disable <REMINDER_ID>` — deactivate one owned reminder.

Activation is independent for each owned reminder. An inactive reminder remains editable unless revoked or otherwise restricted. Active status and shareable permission are separate properties.

When a Custom Reminder is disabled, the runtime automatically uses the corresponding Server Default Reminder, then the built-in default if no server override exists.

### 7.4 Sharing and transfer

- `<PREFIX> r send @USER <REMINDER_ID>` — gift/transfer a reminder, following the existing intended ownership model.
- Require explicit confirmation.
- Only reminders marked shareable may be transferred.
- Record transfer history.
- On successful transfer, invalidate the previous owner's permissions and update ownership atomically.
- Do not confuse sharing a preview/message with transferring ownership. If the existing design supports both, keep them as separate operations and document them.
- Validate the new owner and all ownership relationships.

### 7.5 Utilities and help

- `<PREFIX> r tenor <URL>` — resolve or validate a Tenor URL using existing Dragneel support.
- Support Klipy URLs using existing Dragneel support as well; do not remove or bypass the existing Klipy integration.
- `<PREFIX> r help` — display user-facing documentation.
